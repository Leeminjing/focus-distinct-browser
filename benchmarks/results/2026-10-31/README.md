# 2026-10-31：v0.6.2 本机并发基线

结论：**下一项优先调查截图完成链路，而不是先合并 Environment 或优化 Base64。**
当前机器的可用内存限制了扩容；这些结果不能证明整台机器最多支持 5 个 Browser。
本轮没有修改隔离、控制权、恢复、Focus 或 RPC。

## 条件与数据

Windows 11 build 26200，i9-13900HX，32 逻辑核，物理内存 15.70 GiB。
实际子进程 Runtime `156.0.4314.50`。960×720 DIP，144 DPI，1440×1080 窗口，
CSS 视口约 946×619.33；截图为 1419×929 像素，测试页 PNG 约 415 KB。
网页使用固定种子噪声画布；不是外部网站或模型任务。

正式 EXE：v0.6.2，582144 bytes，源提交 `9051180b8ce81a22a127117cbefe2fb4c56df6b4`，
SHA-256 `db1ae1fc8a62debf25fbf8b349ba0e1f62bcb5c4d56a79af58b692e4091eb79b`。
诊断 EXE：607744 bytes，SHA-256
`ee1a86b04a04b88bcca6eb90d452f17bb7b655ea69b918b4abe16946dddd18f3`；
其版本资源仍为 0.6.2，但含本 PR 的可选计时，不能替代正式产物。

所有实测显式使用低内存配置：预留 1.5 GiB 物理可用内存、2 GiB 提交余量、
创建并发 1、采样 0.5 秒、就绪静置 3 秒、预热 1 轮、每页工作负载 20 轮。
这是新 Profile、暖系统缓存；其他日常程序保持运行。没有为了容量关闭用户应用。
默认更保守的 2 GiB / 15% 配置仅做保护检查，没有把它的数据混入下表。

- [`release-01.json`](release-01.json)：第一轮正式 EXE，启动可用内存 2.37 GiB。
- [`release-02.json`](release-02.json)：复测正式 EXE，启动可用内存 2.07 GiB。
- [`diagnostic.json`](diagnostic.json)：独立诊断 EXE，启动可用内存 2.62 GiB。
- 同目录 `*-requests.csv`、`*-resources.csv` 及诊断 `*-native-trace.jsonl` 保留原始数据。

第一轮是工具初测版本：新进程首次发现前的 CPU 未计入区间增量，也未显式采样
关闭后的零值；不能据此比较启动 CPU。它的请求耗时、工作负载资源、原生句柄
退出检查仍保留。后两轮补齐新子进程启动 CPU 和 `post_close` 采样，记录脚本摘要。
最终脚本还让原生计数失败显式触发保护；这些实测的 `sampling_errors` 均为空。
保留两轮差异，避免只展示完成率更高的一轮。

## 正式产物延迟

单位 ms，表格为中位数 / P95，P95 使用 nearest rank，仅统计成功请求。
样本数是每种工作负载操作的次数；点击输入框另列原始 `focus_input`，不混入点击。

| 轮次 | Browser × Page | 样本 | observe | click | text | 整批就绪 | 重连+快照 |

| 01 | 1 × 1 | 20 | 116.7 / 127.4 | 13.7 / 20.3 | 11.4 / 14.1 | 579.9 | 40.4 |
| 01 | 1 × 3 | 60 | 117.1 / 123.5 | 21.8 / 26.1 | 18.5 / 24.6 | 1108.1 | 46.1 |
| 01 | 5 × 1 | 100 | 166.9 / 218.5 | 89.5 / 130.5 | 43.8 / 54.4 | 2912.4 | 89.3 |
| 02 | 1 × 1 | 20 | 113.7 / 132.7 | 8.5 / 11.5 | 7.8 / 9.7 | 611.0 | 33.6 |
| 02 | 1 × 3 | 60 | 109.2 / 117.0 | 11.8 / 13.9 | 14.7 / 16.4 | 1218.9 | 41.1 |

以上 observe / click / text 错误率均为 0。第 01 轮单个 create 中位数约 271–293 ms，
create→首张测试页观察约 573–582 ms（详见 JSON；不能用小样本创建 P95 宣称稳定 SLA）。
批量创建串行准入，整批耗时不能用于推断宿主并行创建能力。

**未完成的场景：**第 01 轮 5×3 在创建阶段触发保护，当时可用物理内存约
1.41 GiB；第 02 轮 5×1 也在创建阶段触发保护，当时约 1.47 GiB。
后续 10×1、10×3、20×1、20×3 均标为 `not_run`，没有继续压测。
保护中断的请求并不代表宿主报告了相同数量的创建失败，不能纳入工作负载错误率。
内存余量随其他应用波动，5×1 只证明一次完成，不能称为稳定容量。

## 原生资源与关闭

工作负载阶段的观测峰值；宿主和 WebView2 后代相加，Python 客户端单列在原数据。
私有内存是 PrivateUsage 提交量；工作集相加含共享页，不能解释为独占物理内存。

| 轮次 / 场景 | 原生进程数 | 私有提交峰值 MiB | 工作集之和峰值 MiB | CPU 峰值（整机容量归一化） |

| 01 / 1×3 | 7 | 349.3 | 554.7 | 4.46% |

| 02 / 1×1 | 7 | 234.5 | 433.5 | 3.15% |

所有已启动场景（包括保护中断场景）都完成了原生进程退出，剩余进程列表为空，
无强制宿主终止、无清理错误；只删除本次 Profile，保留版本缓存。
第 02 轮 1×1 / 1×3 关闭至全部原生进程退出约 247 / 346 ms，保护中断场景约
394 ms；显式 `post_close` 采样的 host 和 webview 进程数、私有提交、工作集均为零。
这只能证明本轮关闭回落，不能证明长期运行无泄漏。

成功场景均验证原 host、Browser / Page / HWND / URL / title / document UUID、
页面输入与计数、选中页面不变，新连接代次不同；浏览器全部停留在人工控制，
旧令牌返回 `invalid_token`。未自动交还，也未重放操作。

## 有证据的下一项

诊断构建计时（ms，中位数；含初始化和预热，存在文件记录扰动）：

| 阶段 | 1×1，23 次 | 5×1，115 次 |
| --- | ---: | ---: |
| layout metrics 回调 | 1.16 | 0.95 |
| CapturePreview → PNG 完成回调 | 98.55 | 147.54 |
| Base64 编码 | 9.03 | 6.26 |
| 图像 JSON 构造 | 0.47 | 0.44 |
| 响应 JSON → UTF-8 | 5.32 | 5.21 |
| observe 开始 → 响应入队 | 121.55 | 165.39 |

**建议下一轮先做截图链路的像素量 / 图像复杂度对照实验，定位并降低观察延迟。**
这些数据支持把调查顺序放在 CapturePreview 完成路径之前，而非先手写 Base64、
替换 JSON 或重做 Profile 隔离。异步等待、截图编码和 UI 回调调度尚未拆开，
不能直接称为“PNG 编码器 CPU 瓶颈”；也不能将这些嵌套阶段的中位数相加或相减。
管道写入与 Python 解码尚未单独计时，不排除其影响。资源池是否值得做仍需在
有足够空闲内存的机器上补齐 10 / 20 Browser 数据后判断。
